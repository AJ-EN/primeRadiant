# The v1 URL contract

**Posted links are an API.** There is no database, so a shared URL is the only copy of that
model that exists. Every link anyone has ever posted has to keep decoding, forever, and you
cannot migrate them, email their owners, or even count them.

This document is the contract. `lib/contract.test.ts` enforces it.

## Status

**Frozen the moment the first link is public.** Until then, breaking changes are free and
this is the cheapest hour you will ever spend. After that, every rule below applies.

## Shape

```
/m?d=<base64url(JSON)>

{
  v: 1,                  // schema version
  s: string,             // the sentence, ≤ 200 chars
  p: Params,             // the six numbers, in engine key order
  a: string[],           // ≤ 5 assumption sentences, ≤ 140 chars each
  i?: ParamKey[],        // fields that were guessed, omitted when empty
  o?: Params,            // origin params, present only on a fork
  f?: string             // origin fingerprint, ≤ 16 chars
}
```

`Params` keys are always serialised in `PARAM_KEYS` order: `startingCash`, `monthlyBurn`,
`customers`, `price`, `churn`, `newPerMonth`.

## Byte budget: 1800 base64url characters

SPEC 5.1 named ~1500 as the point to switch to a short-code service. That number was chosen
so a link stayed tweet-length, which t.co made irrelevant. The real constraint is the ~2000
character line below which every proxy, mail client and chat app is safe. 1800 leaves room
for the `/api/og?d=` prefix, which wraps the same payload a second time.

The caps are derived from the budget, worst case, with every optional field present and
twelve-digit values in all six slots. That worst case measures **1748 characters**, and a
test fails if it ever exceeds 1800.

Enforcement is at the decode boundary: `decodeState` refuses anything longer than the budget
*before* base64-decoding, JSON-parsing or Zod-walking it. `?d=` is hand-editable and
`/api/og` renders on every crawl, so a megabyte of base64 must be rejected on sight.

## Canonical serialisation

One model produces exactly one URL. `encodeState` writes keys in a fixed order, writes
`Params` in engine key order regardless of how the object was built, and sorts `i` because
which fields were guessed is a set rather than a sequence.

This is not cosmetic. `/api/og` ships immutable cache headers keyed on the payload, so an
equivalent-but-differently-ordered string is a cache miss and a duplicate render, and
analytics would count one model as two.

A decode/encode round trip is the identity function. There is a test.

## What you may change

**Safe.** Old links keep working.

- Adding a new **optional** field. Zod strips keys it does not know, so an older client
  reading a newer payload ignores it rather than failing.
- **Loosening** a bound: raising a max, lowering a min, accepting a value previously refused.
- Changing anything not in the payload at all: copy, layout, colours, the chart, the parser
  prompt, the analytics.

**Breaking.** Requires `v: 2` *and* keeping the v1 decoder forever.

- Removing or renaming any field.
- Changing a field's type.
- Making an optional field required.
- **Tightening a bound.** This one is easy to miss: the bounds in `lib/engine.ts` are part of
  the wire contract, not just input validation. Capping churn at 0.5 tomorrow turns every
  live link with churn 0.8 into a broken-link page.

**Silent breaks. Never do these.** They are worse than a broken link, because the model still
renders and is now wrong.

- Changing what a field *means* while keeping its type: churn from monthly to annual, cash
  from dollars to thousands, `newPerMonth` from a count to a rate. Every old link would
  silently redraw as a different business.
- Changing the projection's ordering assumption (churn before signups) without a version
  bump. Same curve, different arithmetic, no way for a reader to know.

If you need one of these, it is a `v: 2` with a new field name, not a redefinition.

## Adding v2

1. Keep `ModelStateV1Schema` exactly as it is. Do not edit it. Do not "clean it up".
2. Add `ModelStateV2Schema` and a `migrateV1ToV2` function.
3. `decodeState` branches on the `v` field and runs the migration for old payloads.
4. Keep `lib/contract.test.ts`'s golden v1 payload passing. That test is the point.
5. Only ever encode v2.

An unknown version decodes to `null`, which renders the broken-link page rather than
guessing. That is deliberate: a link from the future is better refused than misread.

## The golden payload

`lib/contract.test.ts` holds a frozen base64url literal of a fully-populated v1 state. It was
generated once and pasted in, so it is not regenerated by the code it exists to police.

If that test fails, you have broken every link that has ever been shared. Do not update the
literal to make it pass.
